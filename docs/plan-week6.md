# 第6週 作業計画（承認フロー、リリース、JSON 出力、操作履歴、デモ用シード）※承認済み（2026-11-12）

第5週が11/12に終わったため、前倒しで進める。

## 決めたいこと

- **承認は「全体で1件ずつ」処理する**
  - 1つのトランザクションで「4つのマスタの行（master_tables）をロック → 競合の確認 → 再検証 → 本番へ反映 → リリース作成 → 操作履歴」を行い、途中で失敗したらすべて巻き戻す
  - SPEC の「対象レコードをロック」から変える。横断検証は全マスタを見るため、対象の行だけをロックすると、同時に承認された別の変更セットとの組み合わせで生じる不整合を見落とす。本番データを書き換えるのは承認だけなので、承認どうしを順番に並べれば足りる（編集や閲覧は止まらない）
  - 同じ変更セットの二重承認も、ロックの中で状態を確かめて防ぐ
- **競合の検出と、競合したあとの流れ**
  - 次の行があれば 409 で止め、該当する行の一覧を返す
    - 変更セットを作ったあとに、本番側が新しいリリースで書き換えられた行（master_records.release_id で判断）
    - 追加しようとした record_key が、すでに本番にある行
    - 更新・削除しようとした行が、本番から消えている行
  - 承認者が却下 → 編集者が下書きに戻す（このとき基準のリリースを最新に付け直す）→ 今の本番との差分を見直す → もう一度レビュー依頼。差分はいつも今の本番と比べているので、見直しの手間はかからない
- **権限**
  - レビュー依頼：作成者または admin（下書きのとき）
  - 承認・却下：approver または admin（レビュー中のとき）。却下の理由のコメントは必須
  - 下書きに戻す：作成者または admin（却下のとき）
  - 自分が作った変更セットは、admin でも承認できない（SPEC では approver だけを制限していたが、承認の意味をなくさないため admin にも広げる）
  - 「権限がない（403）」と「今の状態ではできない（409）」は分けて返す。検証エラーが1件でもある、または変更が0件のときは、レビュー依頼と承認を 422 で止める
- **リリースの JSON は DB に保存する**
  - Railway のディスクは再デプロイで消えるため、ファイルには保存しない。releases の `export_path` を本文の列 `content`（LONGTEXT）に置き換える
  - MySQL の JSON 型はキーの順番を並べ替えるため、列の並び（sort_order）を保てるよう文字列で持つ
  - 初期リリース v1 の本文は、マイグレーションで今の本番データから作る（v1 のあとはまだ反映していないので同じ内容）
- **反映後の差分**
  - 承認の時点で、反映前の本番の値を changeset_items.before_data に保存し直す。反映済みの変更セットの差分はこの値で表示する（今の本番と比べると空になるため）
- **操作履歴は、コントローラーやサービスから明示的に記録する**
  - 小さなサービス `AuditLogger` を使う。モデルのイベントで自動的に記録せず、「一括保存で追加3件・更新2件」のように操作の単位で意味のある内容を残す
  - 記録は、その操作と同じトランザクションの中で行う
  - 記録する操作：ログイン、変更セットの作成・編集・削除、データの一括保存（件数だけ）、変更の取り消し、CSV の取り込み、レビュー依頼、承認（バージョン）、却下（コメント）、下書きに戻す
  - ログインの失敗は記録しない（回数の制限はすでにある）
  - `created_at` のインデックスは今は足さず、第7週に100名規模のデータで EXPLAIN を見てから判断する

## 作業手順

### ステップ1：承認フローの API

- `POST /api/changesets/{id}/submit`・`approve`・`reject`・`reopen`
- ChangesetPolicy に上の権限を追加する。承認の処理は `ChangesetApproval` サービスにまとめる
- マイグレーション：releases の `export_path` を `content` に置き換え、v1 の本文を作る
- 変更セットの API が返す `can` に submit・approve・reject・reopen を足す
- 差分 API：反映済みのときは保存した before_data を使う
- PHPUnit：状態・役割ごとの 403 / 409 / 422、自分の変更セットを承認できないこと、承認後の本番データ・バージョン・JSON、競合で 409 になり何も変わらないこと、途中で失敗したら巻き戻ること、反映済みの差分

### ステップ2：操作履歴の記録

- `AuditLogger` を作り、上の各操作から呼ぶ
- PHPUnit：操作ごとに記録が1件でき、detail の中身が正しいこと

### ステップ3：承認フローの画面

- 編集画面に「レビューを依頼」。エラーがある・未保存の編集がある・変更が0件のときは押せず、理由を表示する
- 詳細画面に状態に応じたボタン（承認、コメント付きの却下、下書きに戻す）、却下の理由と承認者。409（競合）のときは該当する行と次にすることを表示する

### ステップ4：リリースの API と画面

- `GET /api/releases`（ページ送り、変更セットと反映した人を一緒に返す）、`GET /api/releases/{version}/export`（JSON のダウンロード）
- `/releases` 画面：一覧、変更セットへのリンク、JSON のプレビュー（開閉式）とダウンロード

### ステップ5：操作履歴の API と画面

- `GET /api/audit-logs`（approver と admin だけ。利用者・操作・期間で絞り込み、ページ送り）
- 絞り込み用の `GET /api/users`（id・名前・役割だけ）
- `/audit-logs` 画面。対象の変更セットへのリンクを付ける。ナビゲーションには見られる人にだけ出す

### ステップ6：デモ用シード

- 下書きの変更セット1つ（SPEC の4つのエラー：HP が 0 の敵、ステージ外の敵配置、ボスが2体いるステージ、削除する攻撃パターンを参照している敵）
- 反映済みの変更セット1つ（承認のサービスを通して作り、v2 のリリースと操作履歴もできる）
- 本番はシード済みのため、デモ用のデータがまだないときだけ入れるコマンドを作り、`docker/start.sh` から呼ぶ（何度実行しても1回分だけ）

### ステップ7：確認と仕上げ

- SPEC 11章のデモの流れを、ブラウザで最初から最後まで通す（編集者 → 承認者 → リリース → 操作履歴）
- CLAUDE.md の進捗と、SPEC の差分（ロックの範囲、admin も自分の変更セットは承認できない、JSON を DB に保存）を更新する
- 本番へのデプロイを相談する（今回はマイグレーションがある）

## 範囲外

- レビュー中の変更セットを、作成者が自分で取り下げる機能（却下 → 下書きに戻す、で対応する）
- 承認を押す前に、競合を前もって表示すること
- ユーザー管理と、操作履歴のインデックス（第7週）
